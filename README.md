# מטבחון – מערכת ניהול קייטרינג ואירועים

מערכת אחת לניהול כ־300 אירועים בשנה בארבע נקודות: **יקב**, **עדן על המים**, **חוות עמק איילון** ו**אירועי חוץ**.
יחידת העבודה התפעולית היא **אירוע**; יחידת הקשר המסחרי היא **לקוח**.

## הרצה

דרישות: Node.js 22.18 ומעלה (נבדק על Node 24).

```bash
npm install
npm run seed      # מאפס את מסד הנתונים וטוען נתוני הדגמה
npm run dev       # שרת API על 8787 + ממשק על http://localhost:5173
```

כניסה בסביבת ההדגמה: כל משתמש `*@demo.local` עם הסיסמה `demo1234`, או בלחיצה על התפקיד במסך הכניסה.

ייצור:

```bash
npm run build && DEMO_MODE=0 npm start   # שרת אחד על PORT (ברירת מחדל 8787) שמגיש גם את הממשק
```

בדיקות: `npm test` (כללי עסק + תרחישים מקצה לקצה על מסד בזיכרון), `npm run typecheck`.

### גיבוי ושחזור

- השרת שומר כל יום גיבוי של מסד הנתונים ושל הקבצים שהועלו ב-`data/backups/`, ובודק אותו מיד: שהוא נפתח, תקין, ומכיל אותו מספר רשומות כמו המערכת. מספר הגיבויים שנשמרים – בהגדרות.
- גיבוי ידני: `npm run backup`, או בהגדרות ← "גיבוי מסד הנתונים עכשיו".
- שחזור (כשהשרת עצור): `npm run restore` מציג את הגיבויים, `npm run restore -- <שם>` משחזר. לפני השחזור המצב הנוכחי נשמר כגיבוי "לפני שחזור".
- כדאי להעתיק את `data/backups` גם למקום אחר (כונן חיצוני / ענן) – גיבוי על אותו מחשב לא מגן מתקלה במחשב עצמו.

### עותק בדיקה לצד המערכת

```bash
DATA_DIR=/path/to/copy PORT=8788 node server/index.ts      # שרת על עותק נתונים
WEB_PORT=5174 API_PORT=8788 npx vite                       # ממשק לעותק
```

## ארכיטקטורה

```
shared/      כללי העסק – משותפים לשרת ולממשק, ללא I/O
  domain.ts       נקודות, מסלולים, מצבים, סוגים
  permissions.ts  מטריצת הרשאות: תפקיד × אזור × רמה (צפייה/עריכה/אישור) × נקודה
  kitchen.ts      אורחים → מנות → חומרי גלם, עומס שבועי, השפעת שינוי אורחים
  inventory.ts    הקצאת מלאי בין אירועים, פערי קבלה
  readiness.ts    מוכנות מחושבת מהנתונים לפי כללי הנקודה
  finance.ts      מצב גבייה (באגורות בלבד)
  menuDiff.ts     השוואת גרסאות תפריט
  domain.ts       גם: 8 שלבי התהליך ו"נסגרת כאשר" (DONE_WHEN)
  config.ts       שכבת התצורה: מחילה את הנקודות, הסוגים, השלבים, המונחים וההרשאות של העסק על המילונים בזמן ריצה
  tasks.ts        קטלוג המשימות האוטומטיות
server/      Node + Hono + SQLite (node:sqlite)
  core/           מסד נתונים ומיגרציות, אימות והרשאות, תיקון שדות עם בקרת התנגשות, יומן ביקורת, ערוץ עדכונים
  features/*      events, clients, sales, menu, kitchen, inventory, purchasing, catalog, operations, finance, documents, tasks, overview, admin
  seed/demo.ts    נתוני הדגמה לתרחישי האפיון
web/src/     React + React Query + Tailwind
  ui/             רכיבים משותפים (כפתורים, טפסים, טבלאות, דיאלוג, תגיות מצב)
  lib/            API, הרשאות, עדכון חי (SSE), טופס עם זיהוי התנגשויות
  features/*      מסכים לפי תחום
tests/       בדיקות כללי עסק ותרחישים מקצה לקצה
```

עקרונות:
- **כסף באגורות** (מספר שלם) בכל המערכת; חלוקה ב־100 רק לתצוגה.
- **ההרשאות נאכפות בשרת** בכל נקודת קצה, כולל הסתרת סכומי חוזה ממי שאין לו הרשאת גבייה. הממשק מסתיר את מה שאין הרשאה אליו.
- **עריכה במקביל:** הלקוח שולח רק שדות ששונו וערכי המקור; התנגשות באותו שדה מחזירה 409 עם הערכים, שדות שונים מתמזגים.
- **משימות אידמפוטנטיות:** מפתח ייחודי לכל טריגר; `reconcileEvent` רץ אחרי כל שינוי ובסריקה תקופתית.
- **מלאי כספר תנועות:** אין עדכון יתרה ישיר – רק תנועות (קבלה, צריכה, העברה, ספירה, התאמה).
- **יומן ביקורת** לכל שינוי מהותי; היסטוריה בכל אירוע.

## גבולות בשלב זה

לפי סעיף 7 באפיון: השיבוץ ב־Ubeya והרישום בהנהלת החשבונות נשארים בתהליכים הקיימים – במערכת מתעדים ידנית סיכום צוות, אסמכתאות תשלום ואחריות למעקב. חיבורים אוטומטיים לא נבנו.

ההחלטות העסקיות בסעיף 7 (מועדי נעילה, זמני יעד, מקדמי כמויות ועוד) מוגדרות בברירות מחדל סבירות וניתנות לשינוי במסך ההגדרות – יש לאשר אותן מול ההנהלה לפני העלייה לאוויר.
